# 海洋生态数字电子书 Web 端设计规格

## 1. 目标与边界

本规格定义实训项目的第一阶段：在 20 个工作日内交付可部署、可演示的海洋生态数字电子书 Web 平台。

本阶段实现海洋科普内容管理、公开阅读、用户互动和基础统计；不实现 RK3568、语音交互、端侧大模型、TCP 网关或嵌入式代码。后续终端只能经后端资源查询接口获取内容，不能直接访问数据库。

## 2. 技术方案

- 运行时：JDK 17、Spring Boot 3、MyBatis-Plus、MySQL 8。
- 前端：Vue 3、Vite、Ant Design Vue、Vue Router、Axios。
- 认证：JWT；后端负责所有角色权限校验。
- 接口文档：Swagger/OpenAPI。
- 发布：Linux 测试服务器、Docker Compose、Nginx。
- 增强项：Redis、OSS、WebSocket、RocketMQ、JMeter；不阻塞首期验收。

采用单体 Spring Boot 后端和单个 Vue 工程。Vue 工程按 `portal`、`admin`、`shared` 模块划分；Spring Boot 按 `auth`、`content`、`interaction`、`dashboard` 和 `common` 模块划分。

```text
Browser → Vue 3 (portal / admin / shared) → /api
       → Spring Boot (auth / content / interaction / dashboard)
       → MySQL 8
```

开发时由 Vite 代理 `/api` 到 Spring Boot。部署时由 Nginx 托管前端静态文件并反向代理 `/api`。

## 3. 用户与权限

- 访客：只能浏览已发布的分类、电子书和章节。
- 注册用户：在访客权限基础上，可点赞和收藏电子书。
- 管理员：可管理分类、电子书、章节、发布状态和基础统计。

首期使用 `users.role` 固定角色字段，值为 `ADMIN` 或 `USER`；访客没有账户记录。暂不实现可配置角色、权限、菜单和操作日志的通用 RBAC 与审计系统。

前端以路由守卫改善体验；后端根据 JWT 和角色再次校验，任何管理员接口不得只依赖前端隐藏。

## 4. 内容与数据模型

内容采用“分类 → 电子书 → 章节文档”三级结构：分类使用 `parent_id` 支持多级主题；一本电子书归属一个分类；章节文档归属一本电子书并保存富文本正文。

首期数据表：

- `users`：账号、密码哈希、角色、状态和时间字段。
- `categories`：名称、父分类、排序和状态。
- `ebooks`：分类、标题、封面、简介、发布状态、阅读量和内容来源说明。
- `chapters`：电子书、标题、富文本正文、排序、发布状态和内容来源说明。
- `tags`、`ebook_tags`：主题标签及其与电子书的关联。
- `favorites`、`likes`：用户与电子书的互动记录，并对 `user_id + ebook_id` 加唯一约束。

首期实现标签、排序、草稿/发布状态；为音视频、版本历史、多语言和 AI 知识库保留扩展空间，但不预先实现通用内容引擎。

所有电子书或章节必须使用自制内容或授权状态明确、可再利用的公开资料，并记录来源、授权依据或署名要求。来源不明的图文、音视频不能进入最终交付版本。

## 5. 页面与接口

用户端流程：`首页 → 分类浏览 → 电子书详情/目录 → 章节阅读 → 登录后点赞或收藏`。

管理端流程：`管理员登录 → 数据概览 → 分类管理 → 电子书管理 → 章节编辑与发布`。

接口按业务划分为：

- `/auth`：登录和注册。
- `/categories`：公开查询及管理员分类管理。
- `/ebooks`：电子书查询与管理员管理。
- `/chapters`：章节阅读与管理员编辑、发布。
- `/interactions`：点赞和收藏。
- `/dashboard`：管理员统计。

后端统一返回状态码、提示信息和数据。前端对未登录、无权限、参数错误和服务异常提供明确提示。后续嵌入式端使用公开、只读的资源查询接口；若将来需要 TCP，由 TCP 适配层调用同一套业务服务。

## 6. 五人分工

1. 项目经理兼文档：需求、任务看板、风险、需求/设计/答辩文档。
2. 用户端前端：分类浏览、电子书详情、章节阅读、点赞和收藏。
3. 后台管理端前端：分类、电子书、章节、统计页面和富文本编辑。
4. 后端兼云端：数据库、接口、JWT、业务逻辑、容器化与 Nginx。
5. 测试兼部署：测试用例、缺陷跟踪、集成验证、发布检查和演示环境。

全体成员参与代码审查和联调。

## 7. Git 协作

- `main`：仅存放可部署、可演示的稳定版本。
- `develop`：集成开发分支。
- `feature/<module>`：从 `develop` 拉出、按功能开发的个人分支。

功能完成后必须经开发者自测、至少一名成员审查、接口文档同步，再合并到 `develop`。不允许直接提交到 `main`。

## 8. 实施顺序与质量门禁

第一段目标是最小可运行骨架，而非业务页面：初始化 Git 仓库与 `frontend/`、`backend/`；启动 Vue 空白页、Spring Boot 健康检查、MySQL 连接和数据库迁移；让前端成功调用健康检查接口；保证每名成员均能在本地启动。

后续顺序：登录与角色 → 分类/电子书/章节后台管理 → 用户阅读与互动 → 统计 → 测试 → Docker 部署 → 答辩与归档。

每项功能的完成定义：能运行、自测通过、Swagger 或接口说明同步、至少一名成员审查、在 `develop` 集成验证通过。

测试包含功能、接口、权限、数据与合规、兼容体验及性能记录。硬门槛是所有必做功能可演示、无阻断缺陷、可按说明部署。性能测试记录环境、数据量、并发和结果，不预设 TPS 数值。

## 9. 20 个工作日里程碑

- 第 1—2 天：需求、内容来源、任务看板、仓库初始化。
- 第 3—4 天：原型、ER 图、接口契约、环境与骨架。
- 第 5—7 天：登录、JWT、权限、分类与电子书基础管理。
- 第 8—10 天：章节富文本、草稿/发布、标签、排序、来源说明。
- 第 11—13 天：用户端浏览、阅读、点赞、收藏。
- 第 14—15 天：基础统计与可选增强项。
- 第 16—17 天：测试、缺陷修复与回归。
- 第 18 天：Docker Compose、Nginx、部署演练。
- 第 19—20 天：答辩演示、代码冻结、`main` 发布和成果归档。

## 10. 团队交付物

团队统一提交：项目源码、需求说明书、设计文档、测试用例与报告、答辩 PPT、演示视频。个人周志和实习报告不纳入本规格的项目交付范围，只在实训过程管理中维护。
